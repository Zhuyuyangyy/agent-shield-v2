## 一、发明名称

**一种面向 AI Agent 的输出合规审计与工具调用影子预演熔断方法及系统**

## 二、技术领域

本发明属于人工智能安全审计领域，具体涉及 AI Agent（人工智能代理）的输出文本合规性审计与工具调用行为风险控制技术。

## 三、背景技术与问题

### 3.1 背景

大型语言模型（LLM）驱动的 AI Agent 正在成为企业自动化的核心组件。AI Agent 不仅生成文本输出，还通过工具调用（Tool Call）执行数据库查询、文件操作、邮件发送、网络请求等高敏感行为。然而，现有 AI Agent 框架缺乏对工具调用风险的事前审计能力——只有在危害已经发生之后才能发现。

典型风险场景包括：

- **财务 Agent**：被诱导执行 `SELECT phone, id_card, bank_account FROM customers` 并将结果发送到外部邮箱
- **客服 Agent**：批量导出用户隐私数据用于未授权分析
- **代码 Agent**：执行有害 SQL 命令（DELETE/UPDATE）导致数据损坏
- **多 Agent 协作**：单一低风险 Agent 的行为在组合后产生系统性数据泄露

### 3.2 现有技术缺陷

| 缺陷 | 描述 |
|------|------|
| 无事前风险预测 | 工具调用执行后才能发现风险，无法阻止危害发生 |
| 缺乏工具调用标准化 | 不同工具的调用格式各异，无法统一审计 |
| 敏感数据识别粗粒度 | 仅按表级别或字段名匹配，无法感知"哪个 Agent、在什么上下文、访问什么数据" |
| 无外部传输检测 | 无法识别 AI Agent 试图将查询结果发送到外部系统 |
| 输出与行为审计割裂 | AI 输出审计（V1）和工具调用审计（V2）各自独立，无法形成统一风险视图 |

## 四、发明概述

本发明提出一种**双通道 AI Agent 风险审计与熔断控制系统**，同时覆盖：

- **输出侧审计（V1）**：对 AI 模型生成的文本输出进行幻觉检测、RAG 溯源、风险熵评分和硬门控
- **工具侧审计（V2）**：在工具调用执行前通过影子预演预测风险，计算影子风险评分并触发熔断

其核心思想是：**AI Agent 的风险既存在于"说什么"（输出），也存在于"做什么"（工具调用）；必须同时控制输出和工具调用两个通道，才能实现真正的 AI Agent 安全治理。**

### 5.2 工具侧审计核心流程（V2）

**第一步：工具调用标准化（ToolCallRequest）**

将所有工具调用统一为标准格式：

```python
@dataclass
class ToolCallRequest:
    tool_name: str           # 工具名称，如 "cursor.execute", "send_email"
    params: dict             # 工具参数，如 {"sql": "...", "to": "..."}
    agent_id: str            # 调用者 Agent 身份
    session_id: str          # 会话追踪 ID
    is_database_tool: bool   # 是否为数据库操作
```

**第二步：SQL 结构解析（SQLAnalyzer）**

通过正则表达式解析 SQL 语句，提取：

- 操作类型（SELECT/INSERT/UPDATE/DELETE）
- 目标表名（FROM/INSERT INTO/UPDATE）
- 查询字段（SELECT 后的列名）
- WHERE 条件（用于判断是否为全表扫描）
- 聚合函数检测（COUNT/SUM/AVG 等）

```python
@dataclass
class SQLInfo:
    tables: list[str]              # 涉及的表
    operation: str                  # SELECT | INSERT | UPDATE | DELETE
    selected_columns: list[str]     # SELECT 的字段
    where_conditions: list[str]     # WHERE 条件
    has_aggregation: bool           # 是否含聚合函数
    is_bulk_query: bool            # 是否批量查询（无 WHERE 或跨 3 张表以上）
    sensitive_fields_detected: list[str]  # 检测到的敏感字段
```

**第三步：数据库影子预演（DatabaseShadowSimulator）**

在真实执行前，通过启发式规则预测工具调用的影响：

```python
@dataclass
class ShadowEffect:
    predicted_tables: list[str]          # 预测会访问的表
    predicted_columns: list[str]         # 预测会访问的列
    affected_rows_estimate: int          # 估算影响行数
    sensitive_fields_detected: list[str] # 检测到的敏感字段（含表名前缀）
    data_volume_mb: float               # 估算数据量（MB）
    is_external_transfer: bool          # 是否意图外部传输
    is_bulk_operation: bool            # 是否批量操作
    risk_indicators: list[str]          # 风险指标列表
    summary: str                        # 人类可读摘要
```

影子预演的核心依赖：**数据资产敏感度映射表（TABLE_SENSITIVITY）**

```python
TABLE_SENSITIVITY = {
    "customers":          (0.95, ["phone", "id_card", "address", "email", "bank_account"]),
    "users":              (0.90, ["password", "phone", "email", "name"]),
    "patient_records":    (1.00, ["medical_record", "diagnosis", "treatment", "ssn"]),
    "employee_salary":    (0.98, ["salary", "bank_account", "name", "id_card"]),
    "transactions":       (0.88, ["amount", "account", "counterparty", "timestamp"]),
    # ... 更多表
}
```

**第四步：影子风险评分（DatabaseShadowRiskScorer）**

基于 5 个因子计算加权风险评分（0.0~1.0）：

| 因子 | 权重 | 说明 |
|------|------|------|
| 敏感数据（sensitive_data） | **85%** | 命中的敏感字段 × 表组合（主导因子） |
| 数据量（data_volume） | 5% | 影响行数、数据体积 |
| 批量操作（bulk_operation） | 5% | 无 WHERE / LIMIT>100 |
| 外部传输（external_transfer） | 3% | email/webhook/ftp 等外发 |
| 操作类型（operation_type） | 2% | SELECT/INSERT/UPDATE/DELETE |

**权重设计原则**：敏感数据权重（85%）主导，确保含敏感字段的查询能冲上 0.90+ 触发阻断，同时保留人工复核空间。

**第五步：熔断决策（RiskFuseController）**

| 评分区间 | 动作 | 说明 |
|---------|------|------|
| score >= 0.90 | **block** | 高风险，直接阻断执行 |
| 0.50 <= score < 0.90 | **human_review** | 中风险，转人工复核 |
| score < 0.50 | **allow** | 低风险，放行执行 |

## 六、核心创新点

### 创新点 1：工具调用标准化抽象

**现有技术问题**：不同工具（数据库、邮件、文件、网络）的调用格式各异，无法实现统一的审计框架。

**本发明方案**：将所有工具调用抽象为 `ToolCallRequest` 统一格式，实现跨工具类型的一致性审计。

### 创新点 2：数据库影子预演机制

**现有技术问题**：工具调用的风险只能在执行后才能发现，无法事前阻止。

**本发明方案**：在真实执行前，通过 SQL 结构分析（正则解析 + 表名/字段名提取 + WHERE 条件分析）预判工具调用的实际影响，无需实际执行数据库即可识别风险。

### 创新点 3：数据资产敏感度双层映射

**现有技术问题**：敏感数据识别仅依赖字段名模式匹配，精度不足，且无法区分不同表的同一字段名的敏感度差异。

**本发明方案**：`TABLE_SENSITIVITY`（表级）+ `_BASE_SENSITIVITY`（字段×表组合级）双层映射，确保敏感数据识别既覆盖表级别风险，又精确到字段级别。

### 创新点 4：影子风险评分与熔断控制

**现有技术问题**：缺乏统一的工具调用风险量化标准，无法在风险高低和响应动作之间建立精确映射。

**本发明方案**：5 因子加权评分模型（敏感数据主导，权重 85%）+ 三档熔断阈值，实现从"风险识别"到"执行控制"的闭环。

### 创新点 5：输出—工具双通道融合审计

**现有技术问题**：AI 输出审计和工具调用审计各自独立，无法形成统一的风险视图。

**本发明方案**：通过 `AuditLogEntry` 融合输出侧和工具侧审计结果，生成综合风险画像，实现对 AI Agent "说什么"和"做什么"的全链路审计。

### 创新点 6：fail-safe 保守策略

**核心原则**：不可解释的工具调用，不自动执行。

- SQL 解析失败 → human_review（保守阻断）
- 影子预演异常 → block（保守阻断）
- 未知工具类型 → human_review
- 无 WHERE 的批量查询 → human_review（保留人工判断空间）

## 八、权利要求初步框架

### 独立权利要求（1）

一种面向 AI Agent 的双通道风险审计与熔断控制方法，其特征在于，包括：

**输出侧审计通道**，包括：
- 接收 AI Agent 的文本输出
- 对所述文本输出进行幻觉检测，识别其中包含的虚假或捏造信息
- 基于检索增强生成 RAG 链路，对所述文本输出中的引用进行溯源验证
- 计算所述文本输出的风险熵评分
- 根据所述风险熵评分和幻觉检测结果，执行输出侧熔断决策

**工具侧审计通道**，包括：
- 接收 AI Agent 发起的工具调用请求，将所述请求标准化为统一的工具调用请求格式
- 通过影子预演引擎，在所述工具调用真实执行前，预测其对数据资产的访问范围
- 基于数据资产敏感度映射表，识别所述工具调用是否涉及敏感数据
- 计算影子风险评分
- 根据所述影子风险评分，执行工具侧熔断决策

**融合审计层**，包括：
- 将所述输出侧审计通道和工具侧审计通道的审计结果写入统一审计日志
- 生成包含综合风险评分的审计报告

## 九、技术优势总结

| 优势 | 说明 |
|------|------|
| **事前防御** | 在工具调用执行前预测风险并阻断，而非事后补救 |
| **双通道覆盖** | 同时控制 AI "说什么"（输出）和"做什么"（工具调用） |
| **可解释审计** | 每一次熔断都有完整的风险因子分解和证据链 |
| **fail-safe 保障** | 不可解释的调用默认阻断，不自动放行 |
| **轻量可部署** | 影子预演无需真实数据库连接，零侵入部署 |
